# Whole-program benchmarks: Dazzle against C++

`tests/bench` compares Dazzle and C++ one construct at a time: an indexed load, a
destructor, a virtual call. That shows the constructs compile to the same thing. It does not
show what a *program* costs. These do: five programs a C++ programmer would recognise as
real work, each written twice, idiomatically, and timed end to end (T-0090).

| Program | What it does | What it leans on |
|---|---|---|
| `astar` | 200 A* searches across a 400×400 grid with 30% walls | a generic binary heap bounded by `Ord`; `HashMap` keyed by a struct with its own `Hash`; two maps, a heap and a path allocated and dropped per search; bounds-checked grid reads; optionals |
| `expr` | generates 100,000 `let` statements (8 MB of text), tokenizes them, parses each into a tree and evaluates it; about one in eight fails on purpose | `String` building, `str` views as tokens and map keys, a tagged union of `Box`es (a tree that frees itself), recursion, `!->` errors propagated with `or return` |
| `json` | generates 100,000 records as a JSON document (17 MB), parses it into a tree, turns the tree into a `List<Record>`, and writes the records back out compactly (13 MB) | a parser over bytes reporting through `!->`, a recursive tagged union of `String`s and `List`s built and freed, `parse_f64` and float formatting, copying text out of the tree, and a writer written once against reflection's type table (the C++ half writes `to_json` by hand) |
| `raytrace` | renders the ray tracer of `examples/stb`, without the PNG, at 960×540 with 16 rays a pixel: spheres, a checkered floor, soft shadows and mirrors | `f32` arithmetic through `std::math`'s `Vec3` and its operator traits, small structs passed and returned by value, `sqrt`, `pow`, `exp`, `sin` and `cos`, tagged unions switched on in the inner loop, `Hit?` returned from every intersection test, recursion |
| `words` | generates 2,000,000 words of text (13 MB) and counts every distinct word, then sorts the counts | `split_whitespace`, a reused `String` buffer, hashing and comparing text, looking a `String` key up by `str`, copying `String`s, `sort_by` |

Each program is a folder: `src/main.dz` and `dazzle.toml` are the Dazzle half, and
`main.cpp` is the C++ half.

## The rules

- **The C++ is what a reviewer would accept.** `std::vector`, `std::unordered_map`,
  `std::priority_queue`, `std::string` and `std::string_view`, `std::unique_ptr`,
  `std::variant` with `std::visit`, `std::sort`. RAII throughout, nothing hand-tuned that
  the Dazzle side lacks, and nothing tuned on the Dazzle side either: each half uses its own
  standard library the obvious way, as benchmarks between languages usually do. So a
  ratio includes each library's design choices, and a report says so where one decides
  it. The largest is the hash table: Dazzle's `HashMap` is a SwissTable, one array of
  slots probed eight at a time, where `std::unordered_map` allocates a node per entry.
  That is most of `astar`'s lead: measured once with Dazzle's map, heap and sort ported
  line for line into the C++ half (2026-11-04), `astar` was even with C++ (1.00× and
  1.01×), `expr` 1.13–1.19× and `words` 1.13–1.29×.
- **Memory goes where each language puts it.** Dazzle code names no allocator: the
  compiler places each value (spec §14.6), in the region of the function that builds it
  when it never leaves, where the caller keeps it when it is returned, and on the heap
  otherwise. Every build places memory so (T-0152); `DZ_REGIONS=0` puts everything on
  the heap, and `tools/bench_regions.py` measures the two against each other. Until r104 the programs chose by hand:
  `expr` put each statement's tree in the per-thread arena `Allocators::Temp`, reset
  before the next, and `words` its whole count, each 5–11% faster for it, while `astar`
  kept the heap, which the arena made about 5% slower and 30% larger. Placement does not
  reach those allocations yet; T-0119 records what that costs. The C++ halves use the
  default heap allocator, which is what the standard containers do unless asked otherwise.
  C++17 can be asked: `std::pmr::monotonic_buffer_resource` is the same idea. So these
  numbers compare each language used the way its own library suggests, not two identical
  allocation strategies.
- **Both halves compute the same thing.** The input is generated by the same SplitMix64,
  written out on both sides, and every program prints a `checksum` line that covers its
  whole result, not just its size: the path cells in order, every statement's value, every
  word with its count in sorted order. Orders that could tie are made total, so the two
  halves agree even though their heaps and sorts are different algorithms.
  `raytrace`'s checksum is over the image's bytes, as a PNG would hold them, and the two
  halves agree on every byte: each float expression is the one the other half writes, in
  the same order, with the same `<cmath>` functions (`sqrtf`, `powf`, `expf`, `sinf`,
  `cosf`, `floorf`), and both are built with `-ffp-contract=off`. Without it a compiler
  may fuse `a * b + c` into one rounding where the target has a fused multiply-add, and
  Dazzle's generated code splits some expressions into statements where the C++ half does
  not, so the halves could fuse differently. On x86-64 without `-march` there is no such
  instruction and the flag changes nothing; built for `x86-64-v3`, both halves fused alike
  and still agreed, but on a different image.
  `tools/bench_programs.py` refuses to report a pair whose checksums differ, and the test
  suite holds every pair to it on a small input (`quick_args.txt`, run by
  `whole_program_benchmarks_agree_with_their_cpp_halves` in `crates/dz/tests/run.rs`).
- **Same compiler, same optimisation.** For each compiler, the Dazzle half is built by
  `dz build --release --cxx <compiler>`, and the C++ half by the same compiler with the same
  flags: `-std=c++17 -O2 -fno-exceptions -fno-rtti`. Dazzle's generated code also gets
  `-fwrapv`, because integer arithmetic wraps in Dazzle (spec §5.1), and
  `-fno-finite-loops -fno-strict-aliasing`, which define two more things C++ leaves
  undefined (§16.5); those are Dazzle's cost to carry, so the C++ does not get them. A
  program's `cxx_flags.txt` holds flags both of its halves get, the Dazzle half through
  `DZ_CXXFLAGS`: `raytrace`'s `-ffp-contract=off`. Without exceptions, C++ reports a failure as a value,
  as Dazzle does; `expr` has the small `Result` type a codebase built that way writes in place
  of C++23's `std::expected`.
- **Timed from outside, as a user would.** Each run is a whole process, generation and
  teardown included, started by a small helper (`measure.cpp`) that also reads its peak
  resident memory. The two halves run alternately, ten times each, and the report gives the
  median. Build time is the median of three builds from a clean `build/` folder, and
  `dz build --timings` says where Dazzle's went, phase by phase.

## Running it

```bash
cargo build --release -p dz
python tools/bench_programs.py                    # every program, clang++ and g++
python tools/bench_programs.py --cxx g++ --runs 20 words
python tools/bench_programs.py --quick            # small inputs: do the halves agree?
python tools/bench_programs.py --markdown tests/bench_programs/RESULTS.md --json out.json
```

Use a release build of `dz`: a debug one makes Dazzle's build time look worse than it is.
Close everything else first; the report prints the load average before and after, and a
busy machine shows up in the numbers.

## Results

The latest run is in [`RESULTS.md`](RESULTS.md), with the machine, the compilers, the
commit and the load average it ran under. Both halves' absolute times move by 10–20% from
one sitting to the next on the same machine, while the ratio within a run moves much less;
compare ratios, and only between halves of the same run.

What the first runs showed (2026-10-24, Ryzen 7 H 255, clang 23 and GCC 16, `-O2`):

- **Dazzle takes 1.3× to 2.1× as long as C++.** It is closer with g++ (1.3–1.45×) than
  with clang (1.55–2.1×) on every program.
- **`words`: the sort is most of the gap.** `List::sort_by` is a heapsort calling its
  comparison through a function pointer; it takes about 100 ms where `std::sort` takes about
  19 ms ([T-0096](../../docs/tasks/T-0096-list-sort-by-heapsort-through-function.md)).
  Generating the text and counting it are within about 1.3×. Peak memory is 71 MiB
  against 32: on the global heap it was 44, and the arena adds the rest, because what a
  growing text or table leaves behind is not reused. Most of the 44 is the words
  themselves: a `std::string` of up to 15 bytes stores its text inline, and a Dazzle
  `String` always allocates.
- **`expr`: parsing is most of the gap.** Every level of the parser returns a union through
  `!->`, and each step costs a default construction, two moves that reset their source, and
  a drop. `Box` is also five times the size of `unique_ptr`
  ([T-0097](../../docs/tasks/T-0097-moving-union-through-fallible-result-costs.md)); it is
  one word since 2026-11-14 ([T-0229](../../docs/tasks/T-0229-box-in-one-word-its-allocator.md)),
  and `Expr` 32 bytes where it was 64, which moved `expr` 2% slower on clang++ and 5% faster
  on g++, and its peak memory not at all, since each statement's tree is dropped before the
  next is parsed. Before
  this benchmark, `let tokens = tokenize(...) or { ... }` copied the whole token list twice.
  That is fixed: it now moves, and peak memory went from 298 MiB to 140, below C++'s 151.
- **`astar`** is 1.3× on g++ and 1.55× on clang. It has not been broken down yet.
- **`raytrace`** (added 2026-11-14, T-0174) was 1.25× its C++ half on clang++ and 1.11× on
  g++. Most of the clang++ gap was one function: `intersect`, private and called from one
  place, was inlined in the C++ half, whose functions are in an anonymous namespace, and not
  in Dazzle's, where it had external linkage. Such functions are now `static` in the
  generated C++ ([T-0221](../../docs/tasks/T-0221-module-private-functions-have-external-linkage.md)),
  and it was 1.10× on both. With a number on the left of an operator typed as the right
  operand (`0.5 * x` was computed in `double`) and a union's `switch` ending in `else`, it is
  1.07×. A hand-written version of its four hot functions on the same types showed the
  shape of the generated code was most of what was left, and on g++ it was one shape: an
  optional assigned its value was built as a temporary through a by-value parameter and
  copied in, and an empty one built its whole payload. With both gone from the runtime
  (2026-11-15) it is 0.97× on g++ and 1.06× on clang++, where what is left is the layout
  of the types
  ([T-0222](../../docs/tasks/T-0222-empty-optional-builds-its-whole-payload.md)).
- **`json`** (added 2026-11-14, T-0173) is 0.99× its C++ half on clang++ and 1.07× on g++,
  since values move by default (r135, T-0235); it was 1.06× and 1.13× before that, the
  furthest behind. It was 1.70× and 1.91× when added, and 1.08× and 1.21× until
  2026-11-15, when its gap and `raytrace`'s were measured not to be the cost of safety:
  with every bounds check and panic compiled out of the generated C++, and the flags that
  define overflow, aliasing and endless loops reversed, neither ran faster on either
  compiler ([T-0234](../../docs/tasks/T-0234-what-kept-json-raytrace-behind-c.md)). What
  was found instead, with what each is worth, is in that task; two were fixed with it, a
  pushed element moved once less and g++'s limit on how far a whole program may grow by
  inlining. About 10 ms of what is left is the benchmark's own: this half writes through
  reflection and the C++ half's writer is by hand. On the way before that: `{}` writes a float's
  shortest digits through `std::to_chars` (r130, D-0101), where it was `snprintf("%g")`; a
  moved-from local that nothing can see is not reset, and `let v = f() or return` names the
  value where it is; `List` starts small; and a `^mut Allocator` is one word (r132,
  D-0103, [T-0228](../../docs/tasks/T-0228-one-word-allocator-handle-in-string.md)), so
  `String` and `List` are 32 bytes where they were 40: that took it from 1.15× and 1.32×,
  and its peak memory from 236 MiB to 208 against C++'s 181. A `List` moving its elements
  as bytes and starting with room for 2 (r134, D-0105) took that to 196 MiB in the same time.
  What is left is in
  [T-0225](../../docs/tasks/T-0225-what-keeps-json-behind-its-c.md). Its writer goes through
  reflection and its reader is written by hand on both sides, since safe code cannot build a
  `String` at a raw address.
- **Build time: 1.7–2.9 s for Dazzle against 0.3–0.5 s for C++.** Dazzle's own phases,
  from reading the manifests to emitting the C++, take about 35 ms of it. Importing
  `stdlib.h` with libclang, which the standard library does for every program, takes
  about 380 ms ([T-0101](../../docs/tasks/T-0101-every-build-imports-stdlib-h-with.md)).
  The rest is the C++ compiler, 1.3 s with clang and 2.1–2.4 s with g++, because the
  standard library's C++ is compiled again in every build
  ([T-0102](../../docs/tasks/T-0102-standard-library-c-compiled-again-in.md)).
