# Whole-program benchmarks: Dazzle against C++

`tests/bench` compares Dazzle and C++ one construct at a time: an indexed load, a
destructor, a virtual call. That shows the constructs compile to the same thing. It does not
show what a *program* costs. These do: three programs a C++ programmer would recognise as
real work, each written twice, idiomatically, and timed end to end (T-0090).

| Program | What it does | What it leans on |
|---|---|---|
| `astar` | 200 A* searches across a 400×400 grid with 30% walls | a generic binary heap bounded by `Ord`; `HashMap` keyed by a struct with its own `Hash`; two maps, a heap and a path allocated and dropped per search; bounds-checked grid reads; optionals |
| `expr` | generates 100,000 `let` statements (8 MB of text), tokenizes them, parses each into a tree and evaluates it; about one in eight fails on purpose | `String` building, `str` views as tokens and map keys, a tagged union of `Box`es (a tree that frees itself), recursion, `!->` errors propagated with `or return` |
| `words` | generates 2,000,000 words of text (13 MB) and counts every distinct word, then sorts the counts | `split_whitespace`, a reused `String` buffer, hashing and comparing text, looking a `String` key up by `str`, copying `String`s, `sort_by` |

Each program is a folder: `src/main.dz` and `dazzle.toml` are the Dazzle half, and
`main.cpp` is the C++ half.

## The rules

- **The C++ is what a reviewer would accept.** `std::vector`, `std::unordered_map`,
  `std::priority_queue`, `std::string` and `std::string_view`, `std::unique_ptr`,
  `std::variant` with `std::visit`, `std::sort`. RAII throughout, nothing hand-tuned that
  the Dazzle side lacks, and nothing tuned on the Dazzle side either: each half uses its own
  standard library the obvious way.
- **Scratch memory goes where each language puts it.** Dazzle's standard library has a
  per-thread arena, `Allocators::Temp`: allocating bumps a pointer, freeing does nothing,
  and `reset()` releases everything at once (spec §14.2). `expr` puts each statement's
  tree in it, reset before the next, and `words` puts the whole count there, since it is
  one batch; each is 5–11% faster for it. `astar` does not: measured both ways, the arena
  made it about 5% slower and 30% larger, because a search's maps grow past the arena's
  64 KiB chunk, so every resize is a `malloc` of its own and the arrays a resize leaves
  behind cannot be reused until the reset. The C++ halves use
  the default heap allocator, which is what the standard containers do unless asked
  otherwise. C++17 can be asked: `std::pmr::monotonic_buffer_resource` is the same idea.
  So these numbers compare each language used the way its own library suggests, not two
  identical allocation strategies.
- **Both halves compute the same thing.** The input is generated by the same SplitMix64,
  written out on both sides, and every program prints a `checksum` line that covers its
  whole result, not just its size: the path cells in order, every statement's value, every
  word with its count in sorted order. Orders that could tie are made total, so the two
  halves agree even though their heaps and sorts are different algorithms.
  `tools/bench_programs.py` refuses to report a pair whose checksums differ, and the test
  suite holds every pair to it on a small input (`quick_args.txt`, run by
  `whole_program_benchmarks_agree_with_their_cpp_halves` in `crates/dz/tests/run.rs`).
- **Same compiler, same optimisation.** For each compiler, the Dazzle half is built by
  `dz build --release --cxx <compiler>`, and the C++ half by the same compiler with the same
  flags: `-std=c++17 -O2 -fno-exceptions -fno-rtti`. Dazzle's generated code also gets
  `-fwrapv`, because integer arithmetic wraps in Dazzle (spec §5.1); that is Dazzle's cost
  to carry, so the C++ does not get it. Without exceptions, C++ reports a failure as a value,
  as Dazzle does; `expr` has the small `Result` type a codebase built that way writes in place
  of C++23's `std::expected`.
- **Timed from outside, as a user would.** Each run is a whole process, generation and
  teardown included, started by a small helper (`measure.cpp`) that also reads its peak
  resident memory. The two halves run alternately, ten times each, and the report gives the
  median. Build time is from a clean `build/` folder.

## Running it

```bash
cargo build --release -p dz
python tools/bench_programs.py                    # every program, clang++ and g++
python tools/bench_programs.py --cxx g++ --runs 20 words
python tools/bench_programs.py --quick            # small inputs: do the halves agree?
python tools/bench_programs.py --markdown tests/bench_programs/RESULTS.md --json out.json
```

Use a release build of `dz`: a debug one makes Dazzle's build time look worse than it is.
Close everything else first; the report prints the load average before and after, and a
busy machine shows up in the numbers.

## Results

The latest run is in [`RESULTS.md`](RESULTS.md), with the machine, the compilers, the
commit and the load average it ran under. Both halves' absolute times move by 10–20% from
one sitting to the next on the same machine, while the ratio within a run moves much less;
compare ratios, and only between halves of the same run.

What the first runs showed (2026-10-24, Ryzen 7 H 255, clang 23 and GCC 16, `-O2`):

- **Dazzle takes 1.3× to 2.1× as long as C++.** It is closer with g++ (1.3–1.45×) than
  with clang (1.55–2.1×) on every program.
- **`words`: the sort is most of the gap.** `List::sort_by` is a heapsort calling its
  comparison through a function pointer; it takes about 100 ms where `std::sort` takes about
  19 ms ([T-0096](../../docs/tasks/T-0096-list-sort-by-heapsort-through-function.md)).
  Generating the text and counting it are within about 1.3×. Peak memory is 71 MiB
  against 32: on the global heap it was 44, and the arena adds the rest, because what a
  growing text or table leaves behind is not reused. Most of the 44 is the words
  themselves: a `std::string` of up to 15 bytes stores its text inline, and a Dazzle
  `String` always allocates.
- **`expr`: parsing is most of the gap.** Every level of the parser returns a union through
  `!->`, and each step costs a default construction, two moves that reset their source, and
  a drop. `Box` is also five times the size of `unique_ptr`
  ([T-0097](../../docs/tasks/T-0097-moving-union-through-fallible-result-costs.md)). Before
  this benchmark, `let tokens = tokenize(...) or { ... }` copied the whole token list twice.
  That is fixed: it now moves, and peak memory went from 298 MiB to 140, below C++'s 151.
- **`astar`** is 1.3× on g++ and 1.55× on clang. It has not been broken down yet.
- **Build time: 1.8–3 s for Dazzle against 0.3–0.5 s for C++.** The front end is about
  0.5 s of that. The rest is the C++ compiler on the generated code, which includes the
  standard library's C++ (about 1 MB of headers) on every build
  ([T-0012](../../docs/tasks/T-0012-measure-compile-time-at-scale.md)).
