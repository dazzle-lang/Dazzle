## Checking under the sanitizers

Spec §1.1 promises that safe code reaches no undefined behaviour, and the evidence is every
program that runs, built under AddressSanitizer and UBSan (T-0132). CI's `sanitizers` job
runs two ignored tests in `crates/dz/tests/run.rs`, which need clang++ with its sanitizer
runtimes:

- `every_program_is_clean_under_sanitizers`: every `tests/run` program, with regions on
  and off (`DZ_REGIONS`), must print its `expected.txt` (or panic as it says) and draw no
  report.
- `headless_examples_are_clean_under_sanitizers`: `examples/ownership` and `examples/stb`
  must run to the end without one.

```bash
cargo test -p dz --test run sanitizers -- --ignored
```

Leak checking is off: a leak is not undefined behaviour, and a program that panics leaks by
design. To build one program the same way, `DZ_CXXFLAGS` adds flags to the command that
compiles Dazzle's code and links it (not to vendored libraries):

```bash
DZ_CXX=clang++ DZ_CXXFLAGS="-fsanitize=address,undefined -fno-sanitize-recover=all -g -O1" cargo run -p dz -- run tests/run/ownership
```

## Fuzzing the ties check

The ties check (spec §6.7) is written by hand and has no formal model, so `tools/fuzz_ties.py`
writes small programs to test it (T-0134). Each takes views into lists, strings, hash maps, a
`Box`, two `Rc`s to one list, a union's payload and a struct's fields; kills memory directly,
through helpers, through two arguments, or somewhere else; and uses the views. An accepted
program is built under the sanitizers with every value on the heap and run, and one they
flag is a hole. A program refused only by the ties check is built anyway, by a debug `dz`
reading `DZ_FUZZ_ALLOW`, and run, to see whether the refusal was needed.

```bash
cargo build -p dz
python tools/fuzz_ties.py --cases 1000 --seed 7
```

A hole is written to `target/fuzz_ties/findings/` as a program of its own, to be cut down and
added to `tests/flow` as a program that must be refused. A refused program that runs clean is
not always a refusal for nothing: the sanitizers see only memory that was freed, so a view
read after `clear()` (which keeps the array), after a union changed variant, or of a long
`String`'s text after the `String` moved, runs clean while it reads what the program no
longer holds.

## What the generated C++ relies on

Spec §1.1 promises that safe Dazzle reaches nothing C++ leaves undefined. This is the audit
behind that (T-0133, 2026-11-04): every operation `dz_cpp` emits or the runtime shim performs
that C++ leaves undefined for some input, and what rules each input out. A new construct in
the emitter belongs in it.

| Operation | What C++ leaves undefined | What rules it out |
|---|---|---|
| `+`, `-`, `*`, unary `-` on integers | signed overflow; `u16 * u16` overflows the `int` C++ computes it in | `-fwrapv` (§16.5); an 8- or 16-bit result is cast back to its type |

| `float as int` | out of range, or NaN | `num::float_to_int` saturates, and NaN is 0 (§10.6) |
| `int as` a narrower signed type | implementation-defined in C++17 | two's complement on every supported compiler; required by C++20 (§10.6) |
| `f64 as f32`, float `/` by 0 | undefined in ISO C++ | defined by IEEE 754, which clang++ and g++ follow (Annex F); UBSan does not flag either |

| `memcpy`, `memmove` of elements | a type C++ does not call trivially copyable | `std` copies bytes only when `T::is_trivially_copyable`; the emitter asserts C++ agrees for every type Dazzle calls so (`static_assert(__is_trivially_copyable(T))`), and a union carrying a struct with a constructor uses C++'s own copy (T-0133) |

| an uninitialised value | reading it | every field is value-initialised (`{}`), and a `switch` used as a value starts from its type's default (§6.2) |
| a pointer cast | reading one type's memory as another (strict aliasing) | only in `unsafe` and `std`'s trusted bodies (the memory tracker's word scan, `TieGuard`); `-fno-strict-aliasing` (§16.5) reads the bytes as the type named. Alignment stays the `unsafe` block's |
| a function returning a value | flowing off its end | the emitter ends every such function with `::dz::unreachable`, a panic, where C++ cannot see that a `switch` returned (§6.4) |

| a loop with no side effects | assumed to end (C++ forward progress) | `-fno-finite-loops` (§16.5): clang++ and g++ deleted `while x < 10 {}` without it (T-0133) |
