1. ✅ **Language groundwork (r39)** — `static`, associated functions, trait objects.
2. ✅ **`#if` and `#location` at the caller (r40).**
3. ✅ **Associated constants (r41).**

What remains, in the order the user set on 2026-09-13:

6. ✅ **Left-to-right argument evaluation** in codegen (r41). Before, a call went to C++ as
   written, and g++ and clang++ on Windows both evaluated `three(say(1), say(2), say(3))`
   right to left; a hoisted argument (`or`, a block value) also ran ahead of the arguments
   to its left. Now `dz_cpp` renders each argument on its own (`capture_args`), then writes
   them out in order (`emit_args`): its hoisted statements, and a temporary only where an
   argument with effects meets one whose value could change — so a call of plain reads
   emits exactly what it did. A value temporary is handed on with `::dz::mv`; a `&T`, and
   the places `construct`/`destroy`/`move_out` work on, are bound by `auto&&` and
   forwarded. A receiver is bound only when an argument has effects, since C++17 already
   sequences the object expression first. Builtins (`println`, `error`…) take the same
   path. `tests/run/argorder` pins calls, a builtin, an `or` clause, a local changed by a
   later argument, a move-only argument and a trait-method receiver; it is in the
   warning-clean set, and g++ was checked by hand too.

   **r44 extended it to every operand**, at the user's request: binary operators
   (`ordered_operands`; `&&`/`||` keep their own short-circuiting lowering), index and
   slice operands (the container held by reference as a place), range bounds and tuple and
   array elements (`sequenced_elements` — C++ braced initialisers are already ordered, so
   only hoisted work needs a temporary), and struct and union literal fields in *written*
   order (`literal_fields` recovers it from the value spans, since the HIR keeps fields in
   declaration order). Assignment evaluates the value before the place — the user's call,
   matching C++17 and Rust — so only hoisted statements needed reordering there. The
   `argorder` fixture grew a case for each. Not touched: a `for` loop's range bounds, which
   are written into the C++ `for` head.

   **The editor: going to a prelude definition.** Ctrl+click on `String`, `List`,
   `Allocators` or `Allocators::Temp` did nothing — the server dropped every location in the
   prelude, whose `<prelude>/dz.dz` path is not a file. `dz lsp` now writes the prelude's
   exact text, read-only, to `%TEMP%/dazzle/prelude-<hash>/dz.dz` and reports locations
   there; a query from inside that copy is answered by any open project's analysis. Two bugs
   found on the way: an associated constant (`Temp`) had no definition at all, and the
   source map holds the prelude under two file ids, only one of them parsed —
   `ide::prelude_file` finds the right one.
7. ✅ **`HashMap<K, V>` and `Hash` (r45).** Open addressing with linear probing over three
   parallel arrays (hashes, keys, values; a zero hash marks an empty slot, so a key whose
   hash is zero is stored as one), doubling at 3/4 full, backward-shift deletion. The
   compiler side: `primitive_implements` gives integers, `bool`, `char` and `str` `Hash`, and
   `str` `Eq`; a prelude trait method called on a primitive (`n.hash()`, `a.cmp(&b)`)
   resolves in `call` and is lowered by `native_trait_call` — `hash` to the shim's
   `::dz::hash`, SplitMix64's finaliser for integers and FNV-1a then that for `str`. Found on
   the way and fixed: `&` of a non-place (`get(&5)`) emitted `::dz::addr(5)`, which C++
   refuses — it now holds the value in a temporary — and its literal ignored the context
   (`&7` wanted as `&u8` was `&i32`); the `&&` lowering wrapped its condition in doubled
   parentheses, which clang warns about; and the unsatisfied-bound help still suggested
   `struct T : Trait`, the spelling r13 replaced. `insert` returns nothing and `replace`
   returns the old value, because a discarded `V?` warns (DZ0510) and most inserts discard
   it. `tests/run/hashmap` (warning-clean, and leak-free under `--track-memory` in
   `a_tracked_build_reports_leaks_and_bad_frees`) checks removal against a reference list

   `Temp`; `typed/` and `typeerrors/` have a case each.

9. ✅ **Math (r48).** Design chosen by the user on 2026-09-13 (18.55): `std::math`,
   `f32` types plus `Vec2i`/`Vec3i`, methods everywhere, column-major.

## r53 — handles: `Rc`, `Weak`, `Box`; `if let` bindings (18.61, 18.62)

Designed with the user on 2026-09-14, over several rounds (see the game readiness list, now tasks in `docs/tasks/`).

- **Syntax**: `dz_ast::IfBinding::mode` — `if let &v` and `if let &mut v`, parsed with the
  `for`/`case` `parse_bind_mode`; the formatter and dump print it.
- **Checker**: `if_let_binding` types the binding as `for_binding` and `case_binding_type`
  do, for `T?`, `&T?`, `^T` and handles; `or` reads through a `&T?` (`MOVE_OUT_OF_BORROW`
  for a move-only one). Handles are anything implementing the prelude trait `Nullable`
  (`nullable`): `null` takes the handle's type, `h == null` becomes `h.is_null()`, and
  `guarded_handle` rewrites the subject of `or`/`if let` to the new HIR node
  `ExprKind::Guarded { guard, init: h.guard(), value: guard.ptr() }` — a pointer, so the
  rest of `or` and `if let` is the `^T` path unchanged.
- **Codegen**: `Guarded` emits the guard as a line of the current C++ block; an `if let` on
  one opens a block of its own so the guard ends with it. `null` of a handle is `T{}`.
  `if let` bindings: `auto&&` to the optional for a reference, a copy otherwise.
- **Flow**: `Guarded` initialises its local like a `let`; a reference `if let` binding reads
  its operand in place instead of taking it.
- **std**: `memory/{nullable,rc_block,rc,weak,box,unguarded}.dz`. One allocation per `Rc`
  (`RcBlock`: counts, allocator, value); the value dropped with the last `Rc`, the block
  freed when the `Weak`s are gone too.
- **Found on the way**: `copyable` answered `true` for every `T?` (a catch-all), so a
  move-only optional counted as copyable; and `or` on a `&u32?` — what `^u32? or return`
  gives — was refused as "cannot fail". Both fixed.
- **Migrated**: `if let p = ptr` that wrote through `p` in `tests/run/dynamic`,
  `tests/run/iterator` and `typed/`.
- Tests: `tests/run/handles` (every form, the guard outliving `self.texture = null`, a `Weak`
  going null, `Box`; leak-free under `--track-memory`; warning-clean), and `tests/errors`:
  `if_let_mut_on_a_read_only_handle`, `if_let_copy_of_a_move_only_target`,
  `if_let_mut_on_a_read_only_pointer`, `or_moves_out_of_a_reference_to_an_optional`,
  `handles_in_use`.

## r54 — stderr, time, and `#[native]`

Asked for by the user on 2026-09-15, with design answers recorded as 18.20, 18.63–18.65.

- **`eprint`/`eprintln`**: two more names in `BUILTIN_FNS`, format-checked as `println`
  is, lowered to `::dz::eprint{,ln}` in `dz_prelude.h` over a `StderrSink`. stdout is
  flushed first so a terminal shows the two in the order they were written. The memory
  tracker's leak report now goes to stderr (the deferral-register row saying it went to stdout for want of
  one is resolved); `a_tracked_build_reports_leaks_and_bad_frees` asserts stdout stays
  empty. `eprintln_writes_to_stderr` checks both streams.
- **`#[native]`**: a known attribute, only on a module-level function and only in `std`
  (DZ0315 otherwise, with `import cpp` as the help). The checker refuses one that has a
  body, type parameters or `!->` (DZ0556). Codegen emits a forwarding shell to
  `::dz::native::<name>`; the bodies are `NATIVE_H`/`NATIVE_CPP` in `dz_cpp::runtime`,
  written as `dz_native.{h,cpp}` and included only by `std`'s translation unit — kept out of
  `dz_runtime.*` so §16.4's "no I/O" shim stays true. **Found on the way**: a module-level
  `fn f() -> u64` with no body was accepted by every phase and failed only at link time;
  it is now DZ0556 (`tests/errors/fn_without_a_body.dz`).
- **Time**: `std/time/{duration,instant,time,native}.dz`. `Duration` is `u64` nanoseconds
  with saturating `-`; `Instant` reads the shim's existing `steady_clock`; `Time::sleep` is
  `Sleep` (milliseconds, rounded up) on Windows and `nanosleep` elsewhere — not
  `std::this_thread`, which MinGW's win32 thread model lacks; `Time::unix` is
  `system_clock`. `tests/run/time` checks the arithmetic exactly and the clocks by what can
  be promised (monotonic, sleep not short, wall clock current); warning-clean on clang++
  and g++.
- **Decided, not implemented** (spec r54): overflow wraps everywhere (18.63 — plain `+` is
  emitted as C++ `+` today, so signed overflow is still UB until codegen passes `-fwrapv`
  or wraps through the unsigned type); `or unreachable` is `__builtin_unreachable` in
  release (18.20 — it still panics in every build); `Rc<Derived>` → `Rc<Base>` (18.64).

## r80 — a recipe can build a library with its own CMake (D-0090, T-0095)

The user chose this on 2026-10-24, after the SDL3 example showed the cost of §15.1's "no
CMake":
- an `SDL_build_config.h` generated by hand for each platform;
- sixty lines of source globs copied from SDL's CMakeLists;
- no macOS at all, since SDL's Cocoa backend is Objective-C.

`cmake = "vendor/SDL"` in a recipe now replaces everything that says how to compile it. SDL's
recipe is four lines, `examples/sdl3/config/` is gone, and `every_example_builds` no longer
skips sdl3 on macOS.

**Where it runs.** Analysis reads a library's headers, and a CMake library's headers are
the ones its install holds, so the build has to come before the import. It cannot be a
phase, since phases are pure functions of their input (invariant 3), and the editor must
never start a minute-long build on a keystroke. So `dz_project::load_for` takes a
`prepare` hook that runs once every manifest is read and before any header is:
- `dz`'s `analyse_for_build` passes one that runs CMake (`native::build_cmake_libraries`),
  so `check`, `fix`, `hir`, `build`, `run`, `test` and `bench` all build it first;
- the editor's `analyse_with` passes one that does nothing.

`dz_project` then reads what the install says (`cmake::read_install`). A header no build has
installed yet is DZ0709, saying why, rather than clang's "file not found". When the hook
reports an error (DZ0708), loading stops, since every header the build should have
installed would only be reported missing too.

**The build.**
- `build/cmake/<lib>/<Debug|Release>/{build,install}` under the root project, one tree per
  configuration.
- `CMAKE_CXX_COMPILER` is `dz`'s compiler and `CMAKE_C_COMPILER` the C driver of its
  family (`c_compiler_for`).
- `BUILD_SHARED_LIBS=OFF` and `CMAKE_INSTALL_LIBDIR=lib`.
- `CMAKE_POLICY_VERSION_MINIMUM=3.5`, because CMake 4 refuses the old minimums many
  libraries still declare.
- On Windows, `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded`, to match the static C runtime
  clang links there by default.
- Ninja when present; on Windows it is required, as CMake's default generator there
  ignores the compiler. CI installs it there if the runner lacks it.

A stamp holds two hashes:
- the setup (compilers, generator, configuration), where a change deletes the tree, since
  CMake refuses to reconfigure one under another compiler;
- everything, including each option and the content of every file under the source folder
  except `.git`, where a change re-runs configure, build and install.

SDL's first build takes about 20 s here, and an unchanged one about 2 s for the whole
`dz build`.

**The link line** comes from the installed pkg-config file: `Libs` plus `Libs.private`,
since the build is static. `Requires` packages are followed when they are installed beside
it, and passed over otherwise (D-0090: never the machine's). `-I` and `-D` from `Cflags`
become the recipe's include dirs and a new `shared_defines`. Unlike a source recipe's
`defines`, those reach every user of the headers. `-pthread` and other flags go to a new
`LinkInputs::flags`. An install with no `.pc` links every library it installed.

Tests:
- `tests/run/cmake` is a small CMake library whose header includes a file the configure
  step writes from the recipe's `options`, and requires a define only its `.pc` gives.
- `run.rs` pins that a library builds once, again when a source changes but not when a

- **`&array` where a `[]T` was wanted did not compile.** `&xs` becomes `::dz::Addr<T[N]>`,

  `every_macro_naming_a_function_pointer_is_imported` in `dz_cppimport/tests/import.rs`.
- **An imported pointer or function-pointer constant was `static_cast` to its Dazzle type**,

  `mini_shout`, a macro over a function pointer taking `char *`.

Not bugs, but things only the compiler's source told:

- **Function pointers stop at callbacks.** A function-pointer typedef is not imported as a
  name (`PFNGLCLEARPROC`), nor is a header's global variable; `as` does not cast between
  function types; an `fn` cannot be compared with `null`; and `(fn…)?` parses as an optional

  is [T-0094](../tasks/T-0094-function-pointers-casts-null-optional-fn.md), at the user's
  request.
- **An integer macro is untyped**, so `SDL_WINDOW_OPENGL | …` needed `let flags: u64` before

- **A generic function's type parameter is not inferred from the type its result is stored

- **A raw string cannot hold a backtick**, so a GLSL comment containing one ends the string
  early and the rest of the shader is read as Dazzle.

## r79 — examples on six C libraries, and what they found

Asked for by the user on 2026-10-24: the repository and the website showed no pictures, and
the only libraries the examples used were raylib and RGFW, which made Dazzle look made for
raylib. Each example is now a project someone can copy to start on that library, with a
README and a screenshot or GIF: `breakout` and `raylib` (raylib), `sokol` (a particle
fountain on sokol_app, sokol_gfx and sokol_gl), `box2d` (Box2D drawn with sokol, two C
libraries in one project), `stb` (a ray tracer saving a PNG through stb_image_write),
`rgfw` (a software-rendered plasma, replacing the empty window), `miniaudio` (a synthesizer
in a real-time audio callback) and `ownership`. sokol, stb, miniaudio and Box2D joined
`examples/vendor/` as submodules; `examples/README.md` is the gallery.

Writing them against libraries nobody had tried found three compiler bugs:

- **`&x` passed to an overload set was ambiguous in C++.** `&x` becomes `::dz::Addr`, a proxy
  convertible to both `T&` and `T*` so codegen need not know the parameter's type. sokol, in
  C++ mode, declares an inline `sg_begin_pass(const sg_pass&)` beside each
  `sg_begin_pass(const sg_pass*)`, and the proxy matched both. A call to an imported function
  now renders its arguments for the parameter types the importer recorded (`Emitter::call`
  computes the signature before capturing the arguments), and `Emitter::stored` settles a
  `&x` into `::dz::as_ptr` or `::dz::as_ref` once the destination is known.
- **A field of an unnamed struct type was left out of the import** (r79). miniaudio's
  `ma_device_config` keeps `struct { … } playback;`, so its format and channel count could
  not be set at all. `Walker::unnamed_field_type` imports the struct as
  `ma_device_config_playback`, spelled `decltype(::ma_device_config::playback)` in C++, which
  `cpp_path` returns for any type that resolves to it; nesting composes as
  `decltype(decltype(…)::gain)`. A template instance's unnamed members are still left out,
  since there is no owner spelling to start from.
- **A `const` array of `str` was emitted `constexpr`**, which `dz::str`'s constructor cannot
  be (it casts a `const char*`). `const_decl` now looks for a `str` inside arrays, optionals
  and tuples, not only at the top.

And two things that are not bugs but cost time, worth knowing:

- **A `static` cannot hold a struct with an array field** unless the array has a default:
  the initialiser must name every field without one, and an array of 4096 particles has no
  constant literal. The sokol example takes sokol's user-data callbacks instead, a pointer
  to a `Fountain` that `main` owns, which is the usual C pattern anyway.
- **RGFW's OpenGL context crashes on this Windows machine**, at the pinned commit and on
  upstream master alike, in plain C as well as from Dazzle, so the RGFW example draws
  through RGFW's software surface instead.

Tests: `tests/run/cinterop` gained `MiniConfig`, a nested unnamed struct with a C++
reference overload beside its function, run end to end; `dz_cppimport/tests/import.rs`
gained `a_field_of_an_unnamed_struct_names_it_through_decltype`; `tests/run/statics` gained

## r78 — `ImplicitAs`, and the orphan rule widened (D-0087, D-0088, D-0089)

What would make a raylib project use raylib's own types without wrappers: `+` on its
structs, and a `String` where it wants a `const char*`. The user chose a trait the source
type implements over a compiler rule special to `String`, and named it after Carbon's.

- **The orphan rule counts a trait's arguments** (`Ctx::impl_is_local`, `dz_check/impls.rs`).
  It had compared only the trait's module and `Self`'s, which D-0031 predates generic traits
  for. Now `Self`, then each trait argument, in order; a bare type parameter before the
  local type stops the search, as Rust's uncovered-parameter rule does. The `DZ0539` label
  and help say so when the trait has arguments, which `Add` always does (`Rhs = Self`), so
  `impl Add for i32` in `typeerrors/` reads differently now.
- **The recipe's module owns the header's types** (`Workspace::recipe_owner`, `dz_project`):
  the module whose `cpp.libs` names the recipe a foreign module was imported by. Traits
  only.
- **`ImplicitAs<T>`** (`std/core/implicit_as.dz`; `String` and `Path` to `cstr`). In the
  checker, `Body::argument` replaces the expression-then-`expect` pair in positional, fixed
  variadic and named arguments: an argument that is not already its parameter's type, and
  whose type (or referent) implements `ImplicitAs<want>`, becomes `Callee::Method { owner:
  ImplicitAs, name: "convert" }` on it — the node a trait-qualified call already is, so flow,
  monomorphization and codegen needed nothing new for it. A parameter type mentioning a type
  parameter never converts. `expect` adds a help when a type converts but not here: not an
  argument, or two conversions away (`implicit_as_help`).
- **`resolve_impl` picks by result type** when no argument decides. A type with
  `ImplicitAs<cstr>` and `ImplicitAs<Meters>` has two impls of one trait whose `convert`
  takes no argument, so the call's own type (`node_ty` in `dz_cpp`, `e.ty` in `dz_mono`)
  chooses. It had taken the first.
- **Not done**: the editor does not yet show where a conversion happens (an inlay hint would).
  A trait object made from an imported type with a trait from a *third* module, under the
  recipe-owner rule, would put its vtable function in the owner's namespace, where C++'s
  argument-dependent lookup does not search; nothing does that yet.
- Tests: `tests/run/implicit_as` (also warning-clean), `cinterop` gained `+` on
  `mini::MiniVec2` and a `String` into `mini_length`, `tests/errors/implicit_as_*`, and a
  section each in `typed/` and `typeerrors/`.

## r76–r77 — struct layout, and projections for every graphics API (D-0085, D-0086)

Both came out of T-0046, which proposed making `Mat4` → raylib `Matrix` free with a pointer
cast and a size assertion.

- **The cast would have been wrong.** raylib declares `m0, m4, m8, m12` first, so its
  `Matrix` holds rows where `Mat4` holds columns; `rlSetUniformMatrix` transposes it back
  before every upload. A cast compiles, passes a size check, and draws transposed. T-0046 is
  now a deferral under `interop` saying so.
- **r76 makes struct layout a rule** (D-0085, §7.3): declaration order, a base's first, C++'s
  padding, never reordered. The compiler already did this; T-0071 assumed it; the spec had
  never said it. No code changed.
- **r77: `DepthRange`** (`std/math/depth_range.dz`, D-0086). `perspective` and
  `orthographic` take it last, with no default. `.ZeroToOne` maps depth as Vulkan,
  Direct3D, Metal and SDL3's GPU API want, where OpenGL's -1..1 had been the only choice.
  `tests/run/math` checks both ranges at the near and far planes for each projection.

## r75 — associated-type projection (T-0050, T-0040)

The user picked T-0050 as the next M12 row: it was the one blocker under generic loops,
iterator adapters and generic arithmetic. Before it, `T::Item` written in a type silently
lowered to the error type, so `fn first<T: Iterate>(it: &T) -> T::Item` checked and meant
nothing. A `for` over a `T: Iterate` or `C: Iterable` was refused with `DZ0801`.

- **`Ty::Assoc(Proj)`** (`dz_hir/src/ty.rs`): a base type, the trait with its arguments, and
  a name. The trait is part of its identity, so `Mul<f32>`'s `Output` and `Mul<Vec2>`'s are
  two types (18.29). While the base is a parameter, or a projection of one (`ty::is_abstract`),
  it is a type of its own. `C::Iter::Item` is a projection of a projection.
- **Normalisation** (`TypeTable::normalize`, `project`). Once the base is concrete, a
  projection becomes what the implementation chose, read through the `impl`'s own
  parameters, so `Numbered<SliceIter<i32>>`'s `(usize, I::Item)` is `(usize, &i32)`. A
  number's `Output` is the number itself, since primitives have no `impl` to say so.
  `dz_hir`'s `substitute` cannot do this, because it has no implementations to look in, so
  **every substitution in the checker, `dz_mono` and `dz_cpp` now goes through
  `TypeTable::subst`/`subst_with`**: the call's solved signature, a field of an instance, a
  trait method read through an implementer, every monomorphized body (`table_body`) and
  every inherited default. `cpp_ty` normalises again as a safety net.
- **Reading through a bound** (`assoc_bindings`): a trait's method read off an abstract type
  binds the trait's associated types to projections of that type. So `it.get()` on a
  `T: Iterate` is a `T::Item`. Before, it was the trait's own `Item` parameter, which every
  `T` shared.
- **Writing one** (`Ctx::project_named`): `T::Name` in a type finds the bound, supertraits
  included, that declares `Name`. None is `DZ0560`. Two, each choosing its own, is `DZ0561`,
  listed in the order the bounds were written.
- **What it can do** (`TypeTable::abstract_bounds`): a projection's bounds are the ones its
  trait puts on the associated type (`type Iter : Iterate`), with `Self` read as the
  projection. They are used for methods and `Trait::m(&v)` calls, `implements`, copyability
  (an `Iterate::Item` is move-only), `needs_drop` and format-spec checks, everywhere a
  `Ty::Param` already was.
- **The two `DZ0801` refusals are gone** from `iterate_item` and `container_iterator`. A
  generic container goes down the same path as a concrete one.
- **Found on the way, and fixed here:**
  - `dz_flow` replayed a loop body with the first pass's moves still on its `for` binding.
    So `for t in it { keep(move(t)) }` was `DZ0401`, with or without generics. Each pass now
    revives the bindings (`loop_body`'s `fresh`).
  - `move(x)` on what an instance makes a `&T` emitted `::dz::take`, which assigned through
    a `const&`. Moving a reference is now a plain copy of it.
  - The `DZ0403` help no longer suggests giving a parameter or a projection a `copy`.
- **Found on the way, and left as tasks:** `(&T)?`, written out or reached through `T?` or
  `T::Item?`, passes the checker and fails in C++. It needs a decision (T-0085). A
  parameter bounded by one trait at two arguments takes the first for a method call
  (T-0086). A stale `books.cpp` in `examples/ownership/build/cpp` failed
  `every_example_builds`, because a build compiles every `.cpp` it finds (T-0087).
- Tests: `tests/run/projection` (generic loops over `Iterate` and `Iterable`, `C::Iter::Item`
  in a signature, an adapter, owned move-only items, `T::Output` for a number and for a
  `Vec2 * f32`; the same output under g++). A case each in `typed/` and `typeerrors/`. Six
  files in `tests/errors/`, one per mistake. `tests/flow/loop_binding_moved_each_pass.dz`.
  A construct and a mistake in the feature matrix, and `dz explain` for both codes.

## r74 — the C heap from `stdlib.h`, and no `alloc`/`free` builtins (D-0084; T-0084)

The user noticed `examples/ownership` calling `alloc` directly, which r11 had said would stop
once allocators existed. They also ruled out a hand-written `extern fn malloc`, since nothing
checks it against the target, so std now imports `stdlib.h` like any C library.

- **The importer takes a requested system header** (`dz_cppimport`, `asked_system_files`).
  `place()` passed over every declaration in a system header, so `import = ["stdlib.h"]`
  imported nothing. Before the walk, `clang_getInclusions` now maps each file to the
  requested header at the bottom of its include chain. A system file whose root is a
  requested system header is admitted, which also brings in `corecrt_malloc.h`, where
  Windows declares `malloc`. A system header that only a library's header includes is
  still passed over.
- **Header import moved from `dz_driver` into `dz_project::load`.** The `dz_check`,
  `dz_flow` and `dz_resolve` test harnesses call `load` and `resolve` directly, and std's
  `libc::malloc` has to resolve there too. For std's import `from_dir` is the temp
  directory rather than the project's `build/cpp`, so the cache key is the same for every
  project and a process parses `stdlib.h` once. Measured on Windows: `dz check` of a
  one-line program went from about 290–390 ms to 350–420 ms. If libclang is missing, the
  error says std needs it, and points at no file.
- **The prelude carries a recipe**: `cpp_deps` `libc`, and `cpp.libs` `libc` importing
  `stdlib.h`, with no sources and nothing to link. Codegen needed nothing new: a module
  with a foreign dependency already emits `#include <stdlib.h>` in its header.
- **`std/memory/c_heap.dz`**: `c_malloc` (panics on null, naming the caller's line, as the
  old builtin did) and `c_free`, behind `Heap`, `TempArena` and the tracker.
  `libc::malloc` returns `^mut void`, and casting it is the one `unsafe` step. The old
  builtin's "alignment stricter than the C heap" panic went with it; `Heap` already
  over-allocates for that.
- **Removed**: `alloc` and `free` from `BUILTIN_FNS`, the checker's arity and type tables,

- **Moved to an `Allocator`**: `examples/ownership` (a `Shelf` that takes

- Tests: `tests/errors/alloc_is_not_a_builtin.dz` and `std_libc_is_not_reachable.dz`

## r73 — `SlotMap<T>` and `Key<T>` (D-0083; T-0004)

T-0004 had been written as a game-specific `Pool<T>`/`Handle<T>`. The user questioned whether
that belongs in `std`, and the answer (D-0083) recast it as a general slot map, with an ECS
ruled out for good.

- **All Dazzle, no `unsafe`.** `std/collections/slot_map.dz` keeps three `List`s: the values,
  densely; the slot each value is in; and the slots, each a version and a `link` that is the
  value's position while taken and the next free slot while free. Removal is `swap_remove`
  on both dense lists, then the moved value's slot is pointed at its new position. With no
  raw memory there is no `Drop` or `Copy` impl to write: a `SlotMap<T>` is copyable exactly
  when its `List`s are (§6.3).
- **Versions by parity**, so `place_of` can refuse an even version before trusting `link`:
  a forged key naming a free slot would otherwise read the free list as a position.
- **`Key<T>` is phantom in `T`**, and the checker needed nothing for that: `Key<Enemy>`
  against `Key<Counter>` is an ordinary `DZ0501`.
- **Found on the way: `&` of a reference was a reference to a reference.** `let s = &mut
  m_slots[i]` typed `s` as `&mut &mut SlotMapSlot`, since `index_mut` already returns a
  reference, and C++ got `SlotMapSlot&& s = ::dz::addr(…)`, which does not compile. The
  same happened for `&mut x` on a parameter `x: &mut P`. The checker's `ExprKind::Ref` now
  takes the pointee of a reference operand, so both are a `&mut T`; nothing in the existing
  corpora changed type. Spelled out in §5.2 as part of r73.
- Tests: `tests/run/slot_map` (stale and null keys, slot reuse, removal from the middle,
  both loops, `retain` dropping one, drops counted exactly, copy, clear, a hundred keys
  through the free list; the same output under clang++ and g++, no leaks under
  `--track-memory`); `typed/` gained a slot map, keys in a field and a map, and `&mut` of a
  reference; `typeerrors/` gained a key of the wrong type and `&mut` of a `&T`.

## r70–r72 — pointer impls refused, defaults at the call, constructors by argument, a generic base (T-0080, T-0058, T-0039, T-0047, T-0036, T-0035)

A batch the user chose on 2026-10-22, with T-0060 and T-0062 (see `tooling.md`).

- **r70: no `impl` for a pointer or reference type** (T-0080, the user chose to refuse rather
  than support it). `impl_placement_ok` reports `DZ0539` for a `^T`, `^mut T`, `own ^T` or
  `&T` self type, generic or not, before the implementation is registered. Method calls peel
  pointers (`Ty::peeled`) in the checker and in codegen, so such an impl was reachable only
  through a bound, where it compiled to a call on the pointee. Nothing in `std` had one.
- **Every default argument is written at the call** (T-0058, closing T-0039 and T-0047 with
  it). `dz_cpp` emitted C++ default arguments on declarations, which C++ reads where the
  function is declared: a default calling a later function, or building a struct defined
  after a trait's handle, did not compile. Now `call` looks up the callee's defaults
  (`callee_defaults` — the instance being called where there is one, an implementation's own
  default before its trait's) and writes every argument the call left out; `decl_params`
  writes none, and the trait handles declare none. A `#location`, `#line`, `#file`,
  `#function` or `#module` default is rendered with the call's span, so it now has the
  column and the Dazzle function name (`Counter::bump_twice`), and the shim's
  `caller_location`/`caller_line`/`caller_file`/`caller_function` builtins are gone. A
  constructor every parameter of which has a default is what `let v: T` runs, and C++ needs
  a real default constructor for that, so `nullary_ctor` gives such a type `T()` delegating
  to it with the defaults, defined beside the constructor. `tests/run/defaults` covers all
  three tasks, built with clang++ and g++.
- **r71: constructors chosen by argument** (T-0036). §7.2 already allowed several, but a call
  took the first. `pick_ctor` keeps those taking that many arguments, defaults counted, then
  those whose parameters the arguments fit (a parameter of the struct's own type parameter
  fits anything), then those every argument matches exactly, a literal matching its default
  type; more than one left is `DZ0538`. A base initialiser chooses the same way. How
  defaults count and that a tie is an error were my choice, written into §7.2 — the user
  had left T-0036's questions open. `tests/run/constructors`.
- **r72: a generic base** (T-0035). `StructSig::base_args` holds the base's arguments in the
  derived type's own parameters, and `TypeTable::args_as(sym, args, ancestor)` reads them
  down a chain. Readers: `flatten_bases` substitutes inherited field types; method lookup
  through a base, override signatures and the base constructor are instantiated at the
  base's arguments; `is_base_of` makes `&Derived` → `&Base<A>` check `A` (and lets a generic
  derived type convert to a non-generic base, which it could not); inherited trait
  implementations look at the base instance. `dz_mono` requests the base instance with the
  derived type's fields; `dz_cpp` names it in `: Base`, in `sort_types` and in `Base::m(self)`.
  As T-0035 guessed, it was an emission-order problem, not a layout one. `tests/run/

## r66 — widths in format specs (T-0005)

Chosen by the user on 2026-10-21 from M12's open tasks: `{:N}` and `{:0N}`, the spelling the
task named, without `{:<N}`/`{:>N}` alignment, which the user left out.

- **Who pads.** T-0005's open question was whether `write_args` pads every argument (so a
  type's own `Format` is padded without cooperating) or the built-in impls pad themselves.
  It is both, split by alignment. Anything else is left-aligned, so `write_args` pads it
  *after* it is written: under a width, `Formatter` counts the characters an argument
  writes (`m_counting`, `m_written`) and makes up the rest with spaces. Nothing is
  buffered, and every output — a `String`, a stream, a panic's message — is handled alike.
  A number is right-aligned, so its padding goes *before* it: the number impls now write
  their whole text in one `write_number` call (the sign moved into `write_digits`' buffer),
  and if that is the argument's first write it is held in `m_held` rather than written.
  When the argument ends with the number still held, it was the whole argument, and
  `end_padded` writes it right-aligned, zeros after the sign under `{:0N}`; if anything
  else is written first, the number is let go as it is and the whole is padded after.
  So `{:12}` on a `Vec2` pads `(1.5, -2)`, not its `x`, and a `Meters` that writes `2.5`
  then `m` pads `2.5m` — the case that rules out "a number at the start pads itself".
- **`width()` and `fill()`** on `Formatter`, for a type that wants to pad itself; one that
  does is not padded again, since it has already written the width. `write_number` is
  `pub(module)`: a number of one's own is right-aligned by padding itself.
- **The checker** (`spec_fits`) reads a spec as `[0][width]` then the rest: a zero fill
  needs a width and a number, a width is a `u32` of at least 1. All are DZ0526 at the
  placeholder, as before. A type's own `Format` and a type parameter are still not checked.
- **`error(…)`** formats in the C++ prelude, without `Format`, so `write_spec` there learned
  the same: a number (`is_number`, overloaded on the fundamental types like `write_value`)
  is rendered into a small buffer and padded in front; anything else goes through a
  `CountSink` and is padded after.
- **`inf` and `nan`** take spaces under `{:0N}`, as C's `%08f` does. The test is that the
  first character after the sign is not an `i` or an `n` — not "is a digit", which the
  first version used and which turned `{:08X}` of `0xBEEF` into spaces.
- Tests: `tests/run/formatting` (every kind, hex, precision, a negative zero-filled, a
  character counted once, a type's own padded whole, a type parameter, `error(…)`); four
  `tests/errors` files, one per new mistake; `typed/` and `typeerrors/` cases.

## CI on 2026-09-15: a dangling view, and an ill-posed test

Linux and macOS CI failed `files`, `text` and `math`; Windows had passed all three.

- **A view outlived its temporary.** Argument ordering (r41) binds an argument to a
  statement of its own when a later one has effects. For `println("{} {}",
  "Héllo".to_ascii_uppercase().as_str(), line.trim())` that was `str _dz_arg =
  to_ascii_uppercase(…).as_str();` — the `String` is a C++ temporary, destroyed at the end
  of that statement, so `println` read freed memory. Windows's heap happened to leave it
  intact. **Fixed**: when the value being bound `borrows` (a `str`, slice, reference,
  pointer, or a struct/tuple/optional holding one), `emit_args` first binds each
  `owning_temporaries` node — a call or literal on the path to the view whose type needs a
  drop — to a local of its own (`Emitter::materialized` renders those nodes as the local), and
  takes the view from that. At the user's suggestion the statement is then put in a scope
  of its own (`stmt`), so the owner is dropped when the statement ends, exactly as the
  temporary was; a `let` is declared first and assigned inside the scope
  (`declare_then_assign`: not for a reference or an imported C++ class, which keep the owner
  to the end of the block). A statement that also took a handle's guard is not scoped, since
  the guard must live to the end of the enclosing block (spec §14.5).
  The `argorder` fixture gained a deterministic case — a `Poisoned` value whose `drop`
  prints and overwrites its bytes — which printed `XXXXX` without the fix on every
  platform, and now pins the drop to right after its statement, `let` included; `text`
  and `files` were run under AddressSanitizer clean.
- **`slerp` halfway to a half turn** has two equally short answers, and which it takes
  depends on the sign of `cos(PI / 2)` in `f32`, which `libm`s disagree on. The test now
  slerps toward a quarter turn.

`loc: &SourceLocation = #location`; core stdlib types in the prelude. Writing that down
showed three things the allocators need that the language did not have, and those are r39.

- **`static`** (§7.7). A keyword, an item, `SymbolKind::Static`, `ItemSig::Static`,
  `BodyOwner::Static` and `hir::ExprKind::Static` beside their `const` counterparts. The
  initialiser must be constants (**`DZ0553`**, `is_static_initialiser`), because C++ builds
  statics before `main` in no promised order across files. A static is a writable place, and
  every way of changing one — assignment, `&mut`, a `&mut self` method, a `for`/`case`
  `&mut` binding, viewing an array as `[]mut` — goes through
  `require_unsafe_static_write` (**`DZ0528`**). Flow treats it as a borrow: nothing is moved
  or copied out (**`DZ0402`**, worded for a static). Codegen writes `inline [thread_local] T
  NAME = …;` after every type; a struct literal's `[&]` lambda is not legal at namespace
  scope, so its capture-default is dropped there.
- **Associated functions** (§7.3). `Quat::identity()` was already in the spec and parsed, but
  a `fn` with no receiver was checked as a qualified method call with its first argument
  taken as the receiver. It is now `hir::Callee::Assoc`, emitted as a C++ `static` member;
  the resolver no longer puts the type's fields in its scope; calling one on a value is
  **`DZ0520`**; `dz_mono` instantiates the owner of `Pair<i32>::both(4)`.
- **Trait objects** (§7.6, 18.6 — decided long ago, owed since M6). `&S`/`^S` convert to
  `&Trait`/`^Trait` in `base_convertible` when `S` implements it; a trait's methods are as
  visible as the trait. In C++ each object-safe trait gets `Shape__vtable` and
  `Shape__dyn : ::dz::Dyn<Shape__vtable>` — two words, forwarding members, null-comparable,
  convertible from `T*`, `T&` and `::dz::Addr<T>`. Each implementation declares
  `dz_vtable(const Shape__vtable*, const T*)` in its own module's namespace and the handle
  finds it by argument-dependent lookup: the orphan rule puts every implementation in the
  trait's module or the type's, which are exactly the namespaces ADL searches, so no
  specialisation or namespace juggling is needed. Default methods are vtable entries like
  any other. Not object-safe (generic trait, associated types, a method mentioning `Self`)
  stays `DZ0801`, as does a trait object of a type whose `impl` is generic.
- **Found on the way.** A `&T` produced by a block or an `if` and stored where a `^T` was
  wanted emitted `(*tmp)` into a pointer and did not compile (`Emitter::stored`, applied to
  `let`, assignment, `return` and struct-literal fields). And **C++ does not define the order
  a call's arguments are evaluated in**, so `println("{} {}", f(), x)` where `f` changes `x`
  printed different things under different compilers — the spec does not say what Dazzle
  promises. Two tests hit it; they now bind first. Raised with the user.
