---
id: T-0103
title: A renamed or removed module's generated C++ stays in build/cpp
milestone: none
status: done
kind: feature
area: tooling
where: `crates/dz/src/build.rs`, `emit_cpp` and `sweep_stale`
---

**Done** (2026-11-14, with T-0194): `emit_cpp` ends with `sweep_stale`, which deletes every
generated `.cpp` and `.h` in `build/cpp` the program is no longer made of, and their objects
in `build/obj/dz`. A file without the generated header line is left alone. No `dz clean`.

**What is missing.** Since T-0087, a build compiles only the files it emitted, so a module
that has been renamed or removed no longer breaks the build. But its `.cpp` and `.h` stay in
`build/cpp/`, and so do the standard library's `.dz` copies for a file `std` no longer has.
Nothing removes them, and there is no `dz clean`. The leftovers take space and confuse anyone
reading the generated C++. Since T-0102 the same goes for `build/obj/dz/`: one object (with
its `.d` and `.stamp`) per generated file and set of flags, so a debug and a release build
keep one each, and a removed module's objects stay.

**What it would take.** Every file `dz` generates starts with `// Generated by the Dazzle
compiler`. So `emit_cpp` can delete any `.cpp` or `.h` in `build/cpp/` that starts with that
line and was not emitted by this build. A file a user put there has no such header and is left
alone, which was the reason T-0087 did not delete anything. A `dz clean` that removes
`build/` outright would be a separate, simpler way to the same end. Compiler work only, for
`docs/log/`.
