**What it is.** A `[cpp.libs]` recipe that names a CMake project instead of listing sources:

```toml
[cpp.libs.sdl3]
cmake   = "../vendor/SDL"                          # a folder with a CMakeLists.txt
options = { SDL_SHARED = "OFF", SDL_STATIC = "ON" } # -D options for the configure step
import  = ["SDL3/SDL.h"]
```

`dz` configures and builds it with CMake, with the same C and C++ compilers it uses itself,
installs it into the project's build folder, and then treats the installed headers and
libraries as the recipe's `include_dirs` and `link_libs`. The link line comes from what the
install describes: the pkg-config file most CMake libraries install (`sdl3.pc`, with its
`Libs.private` for a static build), or CMake's file API where there is none.

**Why it matters.** Spec §15.1 rules this out today: a library with a configure step must
have that step's output generated once and vendored. `examples/sdl3` shows the cost: an
`SDL_build_config.h` per platform generated by hand, and sixty lines of source globs copied
from SDL's CMakeLists, all of which must be redone for every SDL release. macOS cannot be
built at all, because SDL's Cocoa backend is `.m` files, which a recipe does not compile
(`every_example_builds` skips `sdl3` there until this lands). Most of the larger C and C++
libraries a game uses (SDL, Jolt, Assimp, Bullet, OpenAL Soft, freetype) ship a CMake build
and nothing else. With this, any of them is three lines, as raylib is.

**Why it is this way.** "No CMake, no Makefiles, no binaries to find for each platform" was
decided early, for M7a: every library so far was a handful of C files, and a build that is
only `dz` is simpler to explain and to make reproducible. SDL is the first library that
does not fit. **The user chose on 2026-10-24 to add the CMake form**, after the grass work in
`examples/sdl3` and its PR. Source recipes stay as they are for small libraries.

**What it would take.**

1. A decision file reversing §15.1's `[DECIDED]` line for CMake (the source form stays), and
   a §21 revision row. Settle in it: CMake required only when a recipe uses `cmake`, with a
   diagnostic naming it when it is missing; the generator (Ninja when present, else the
   platform default); static libraries by default.
2. `dz_project`: the `cmake` and `options` keys, refused alongside `sources` or `header`.
3. `native.rs`: run `cmake -S root -B build/cmake/<lib> -DCMAKE_C_COMPILER=…
   -DCMAKE_CXX_COMPILER=… -DCMAKE_BUILD_TYPE=… -DCMAKE_INSTALL_PREFIX=build/cmake/<lib>/install`
   plus `options`, then `cmake --build` and `cmake --install`; skip all three when nothing
   under `root` and no option changed, as source recipes skip unchanged objects. The build
   mode picks the configuration.
4. Read the installed `.pc` file for include dirs, libraries and their private dependencies;
   frameworks on macOS come through the same file.
5. Rewrite `examples/sdl3`'s recipe on it, delete `examples/sdl3/config/`, remove the macOS
   skip in `every_example_builds`, and test it with a small CMake project under `tests/run/`.
   CI installs CMake (it is preinstalled on GitHub's runners).
